3. The seven hooks, and what each one catches

HookFires onCatches
session-startSessionStart incl. compactA session starting blind. Injects the contract, the active plan, the current task, gate state, recent evidence. Re-fires after compaction, so a long session recovers.
promptUserPromptSubmitA build request answered by typing code. With no plan open, the research-first rule lands next to your prompt.
pre-editPreToolUse Edit/WriteThe plan gate. Product code before a plan. Advisory, or denied outright in strict mode.
post-bashPostToolUse BashUnverifiable claims. Every test, build, lint and browser command is classified and logged with its result. A failure is reported back as the project's current state.
reanchorPostToolUse Edit/WriteMid-session drift. Every 8th edit, re-injects the current task and the out-of-scope list.
stopStopEnd of turn: code changed with no passing run, or UI changed with nobody having looked at it.
task-completeTaskCompletedCompletion without proof. Exit 2 blocks it in strict mode.

The three gates you can check yourself

forge gate code   # is there a plan with real tasks
forge gate done   # is there passing evidence newer than the last edit
forge gate ui     # did UI change without browser verification

Two details that make these honest rather than decorative:

  • Placeholders do not count. A task line still containing <angle brackets> is scaffold. The gate stays shut until real file paths, tests and commands replace them, so it cannot be opened by generating the template.
  • The done gate compares timestamps, not claims. Evidence recorded before the last edit proves nothing about the code as it stands now. Edit after a passing run and the gate closes again.

Never gated

Tests, docs, markdown, config, .forge/, .claude/, scripts, and anything outside your code directories. There is always a legal next move: writing the plan or the test it demands is never blocked.

Escape hatch, by design. A genuinely trivial fix: forge waive 30 "typo in the error string". Thirty minutes, and the bypass is written to the ledger. The point is not to prevent bypassing, it is to prevent bypassing silently.

4. Advisory versus strict

ModeBehaviourUse for
advisoryGates inject a warning. Nothing is ever blocked.Default. Client work, exploration, anything where an interruption costs more than a skipped step.
strictPlan gate denies the edit. TaskCompleted blocks. A project where quality has actually bitten you. Start with one.

Recommendation: run advisory everywhere for a week, read the ledger, then turn strict on for the one project where the warnings were right most often.

5. The four loops

Four situations, four openings. Each one is a sentence you type, not a command you memorise: the skills trigger on what you say.

A. A brand new project

cd ~/Work/new-thing && forge init
# then in Claude Code:
"here is the brief: <paste>. set this project up."

What happens: forge-intake interviews you, fills a 14-line completeness checklist, asks at most seven questions in one batch with recommended defaults, shows you the assumptions it would build on, and stops. Nothing is generated until you say OK. On your approval it writes the README, the folder structure, CLAUDE.md, .gitignore, .env.example, the test runner with one passing test, the ADRs for the stack decisions, and the first workstream's research, architecture, plan and test-plan. Then it runs forge verify to prove the skeleton builds.

This is the behaviour you asked for. If it starts generating files before you approve, say "you have not shown me the completeness report" and it will stop. The gate is in the skill, and the skill is now auto-loading.

B. An existing project, new feature

cd ~/Work/review-engine && forge init    # once per project
# then:
"add <feature>. research first."

Research reads your codebase before designing, which is what stops a second implementation being built beside the one that already exists. Architecture names the rejected alternatives. The plan gate opens only when tasks carry real file paths and real verification commands.

C. An audit of something that already exists

forge audit
# then:
"audit this project. scope first, reproduce every finding."

Scope and severity are declared before any code is read, so the audit cannot drift into a tour. Eleven systematic passes: cold start, tests, correctness, error paths, auth, secrets, data, UI in a real browser, performance, observability, dependencies. Every finding needs a reproduction; anything that cannot be demonstrated becomes a note, not a finding. It reports, it does not fix, then turns findings into an ordered remediation plan you approve.

D. A bug that keeps coming back

"this is still broken: <symptom>. root cause, not symptom."

debugging-and-error-recovery loads, finds the cause, and the fix becomes a small workstream with a test asserting the bug. A bug fixed without that test is a bug waiting to return, which is the mechanism behind "we fixed this already".

7. Maximum power: what to say

The gates stop the worst outcomes on their own. Getting the best outcome is still about what you ask for. These are the phrases that change the result most, and why each one works.

"research first, then show me the architecture before you write anything"

Forces phases 1 and 2 to be visible and approvable. Most bad builds are bad decisions made silently at minute two, and this is the cheapest moment to catch one.

"show me the plan, I want to approve the tasks before you start"

You review 10 lines instead of 400. A wrong task is seconds to fix; wrong code is an hour.

"what did you actually run? paste the output"

The single highest-value sentence in this entire guide. It converts a claim into evidence, and the ledger means the answer can be checked.

"test counts before and after"

"Tests pass" hides a regression. Two numbers cannot.

"open it in a browser and click every element you touched"

Your recurring complaint, answered directly. Tests do not catch a button wired to nothing or a section that renders empty because the data shape changed.

"review this with a fresh subagent, do not tell it your reasoning"

The author is the worst reviewer of their own work. An unanchored reviewer finds what the author cannot see.

"what is still unverified?"

Surfaces the honest gap instead of a confident summary. Ask it before you believe anything is done.

"is this in the plan? if not, stop"

Cuts scope sprawl the moment you notice it, and amends the plan rather than letting the change drift.

Three habits that compound

  1. Read forge status before you start. Five seconds. It tells you where the last session actually stopped and which gates are red, before you add anything on top.
  2. Make it tick tasks off as they pass. The re-anchor hook reads plan.md. A stale plan produces a confidently wrong anchor, which is worse than none.
  3. Grow the pitfalls file. Every time something bites, one entry. This is the part that makes month three cheaper than month one.

One thing to watch for. If a session ever writes product code somewhere the hook does not look in order to get around a gate, that is a serious failure, not a clever workaround. Tell it so, and turn strict on for that project.

12. What is deliberately not here

  • No embeddings or vector search. A handful of curated files read on demand beats retrieval that returns plausible fragments. Retrieval failure is silent; a missing file is not.
  • No background daemon. Every state change comes from a hook or a command you ran, so the state is always explainable.
  • No blocking by default. A process that fights you on day one gets uninstalled on day two.
